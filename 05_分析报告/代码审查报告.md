## 二、验证通过项（附证据）

### 1. SQL（01_历史窗口_加载与清洗.sql）

- ✅ **清洗规则完备且口径自洽**：`DISTINCT` 去重 → 5 个关键字段非空校验 → 日期范围过滤 + `Price ≥ 0` + 发票类型与数量符号一致性校验（C 发票必须 ≤ 0，非 C 发票必须 ≥ 0）。探索段先 quantify 了异常（C 发票但数量非负的行），清洗逻辑与之呼应。
- ✅ **Shopify 分组映射完备**：穷举 R_score(1–5) × FM_score(1–5) 共 25 格与 CASE 分支比对——10 个分支**无重叠、无遗漏**（"潜客"组在本数据中为空，与报告声明一致）。
- ✅ **FM = FLOOR((F_score+M_score)/2)**：MySQL 中 `/` 为精确除法（5+4)/2=4.5→4，取整正确。
- ✅ **异常处理有依据**：`Monetary ≥ 0` 过滤历史净额为负的 3 名异常客户，且 `Recency` 非空与 `Frequency > 0` 的验证查询保留在脚本中。
- ✅ **统计表防错**：`NULLIF(t.TotalCustomers, 0)` 等写法防止除零。

### 2. SQL（02_未来窗口_与RFM分层与验证.sql）

- ✅ **回测口径正确**：历史 RFM 表 `LEFT JOIN` 未来指标，`COALESCE(..., 0)` 保证未来无交易的客户保留为"未复购"，不丢人。
- ✅ **复购定义一致**：`FutureFrequency` 仅统计非取消发票（`UPPER(TRIM(Invoice)) NOT LIKE 'C%'`），与历史 F 口径对称；未来净M含取消负金额，与文档声明一致。
- ✅ **月度表**：`CROSS JOIN` 5 个未来月份 + `LEFT JOIN`，5,023 × 5 = 25,115 行，与 `customer_monthly_metrics.csv` 行数吻合。

### 3. Python（04_基准lift对比.py / 05_交叉验证.py）

- ✅ **复现口径与 Notebook 完全一致**：`R_days = (2011-07-01 − Recency).days`、`log1p(F/M)`、`StandardScaler`、`KMeans(n_clusters=6, random_state=42, n_init=20)`。
- ✅ **公平 lift 设计正确**：`rfm_key = 组价值序号×1e9 − Monetary`，同一组内按历史 Monetary 降序选出，保证"同一选择人数"下的可比性；满分上界用 `min(..., 1.0)` 防浮点溢出。
- ✅ **η² 手写实现正确**（SSB/SST）；Kruskal-Wallis 与 Mann-Whitney 调用无误。
- ✅ **路径自定位**：`ROOT = Path(__file__).resolve().parent.parent`，任意工作目录可运行（实测通过）。

### 4. Notebook（K-means数据分析.ipynb，42 cells）

## 三、发现的问题与建议（均不阻断开源）

### 🟡 P1 · HTML 报告两处概括性表述与精确值有小出入

| 位置 | 报告表述 | 实际精确值（来自 CSV 复算） | 影响 |
|------|----------|------------------------------|------|
| 摘要/05 节 | Champions 贡献 56.6% 未来净消费、价值密度 4.59 | **56.2%**（0.561746）、密度 **4.56** | 无实质影响 |
| 05 节 | "每一个相同选择人数下，基准都 ≥ 两种分群" | 20% 处 K-means 0.750 > 基准 0.748；30% 处规则RFM 0.825 > 基准 0.822（≤ 0.4 个百分点） | 反超量级远小于低比例段的差距（10% 处落后 7pp），不改变"分群无实质预测增量"的结论；同页 `项目总结.md` 的表述（74.96% vs 74.78%）是精确的 |

**建议**：阅读报告时以 `项目总结.md` 与本仓库数据为准；如需绝对严谨，可将 HTML 05 节措辞改为"基准在几乎所有选择比例下不低于两种分群（个别比例处有 ≤0.4pp 的微小反超）"。

### 🟡 P2 · `05_交叉验证.py` 硬编码 `Cluster == 0`

该脚本用 `champ[champ['Cluster'].eq(0)]` 取 Champions × 最高价值簇交叉单元，依赖 KMeans 标签编号稳定。**实测在 scikit-learn 1.9.0 下标签未漂移**（簇 0 仍为 314 人、输出与文档一致），风险很低；且《项目总结》使用"原簇 **0**"的措辞已明确指向原始编号。跨大版本运行时建议先用交叉表核对簇 0 是否仍为最高价值簇（脚本第一段 crosstab 输出即可判断）。

### 🟢 P3 · `Customer ID` 为浮点样式的字符串

所有客户级 CSV 中该列为 `17592.0` 样式。项目内脚本已统一 `dtype=str` 读取、两表对齐无问题；唯一风险是使用者用 Excel 打开后另存导致格式改变。已在 `03_清洗与派生数据/README.md` 中显式提醒。

### 🟢 P4 · 其他已文档化的口径说明

- `online_retail_ii_clean_history_rfm_statistics.csv` **无表头**（`header=None` 读取）——根 README 与子 README 均已注明；
- R/M 评分基于 `percent_rank`，同日并列客户会落入同一档，档间非严格 20%——属口径选择，报告"局限"节已覆盖（F 分档偏离 Shopify 标准口径亦已声明）；
- 依赖未锁版本——实测 pandas 3.x + sklearn 1.9 宽版本可运行，`requirements.txt` 已注明实测版本。
